# Blocks and the Block Editor

Blocks are the modern way to add editor content. For a plugin, the practical question is whether the block renders in PHP (dynamic) or saves markup to post content (static).

## Scaffolding

```bash
npx @wordpress/create-block myplugin-block
# Inside an existing plugin:
npx @wordpress/create-block myplugin-block --no-plugin
```

This produces the `block.json`, `src/` JS, and build setup using `@wordpress/scripts`.

## block.json

The canonical block definition since WP 5.8. Register from it — do not hand-register in PHP.

```json
{
  "$schema": "https://schemas.wp.org/trunk/block.json",
  "apiVersion": 3,
  "name": "myplugin/feature-box",
  "title": "Feature Box",
  "category": "widgets",
  "icon": "star-filled",
  "description": "A highlighted feature box.",
  "keywords": [ "feature", "box" ],
  "textdomain": "my-plugin",
  "attributes": {
    "heading":  { "type": "string", "default": "" },
    "count":    { "type": "number", "default": 3 },
    "showIcon": { "type": "boolean", "default": true }
  },
  "supports": {
    "html": false,
    "align": [ "wide", "full" ],
    "color": { "background": true, "text": true },
    "spacing": { "padding": true }
  },
  "editorScript": "file:./index.js",
  "editorStyle":  "file:./index.css",
  "style":        "file:./style-index.css",
  "render":       "file:./render.php"
}
```

`apiVersion: 3` is required for the iframed editor (WP 6.3+) and expected for WP 7.0+ compatibility. Older blocks using `apiVersion: 1` or `2` break in the iframed canvas.

## Registering

```php
add_action( 'init', 'myplugin_register_blocks' );

function myplugin_register_blocks() {
    register_block_type( MYPLUGIN_DIR . 'build/feature-box' );   // directory holding block.json
}
```

For several blocks (WP 6.8+):

```php
wp_register_block_types_from_metadata_collection( MYPLUGIN_DIR . 'build' );
```

Register on `init`. The block must be registered in both PHP and JS contexts for the editor and front end to agree.

## Dynamic blocks (rendered in PHP)

Use these when output depends on data that changes after save — recent posts, user state, live values. Only attributes are stored in post content.

```php
// In block.json: "render": "file:./render.php"
```

```php
<?php
// render.php — $attributes, $content, $block are in scope
$heading = $attributes['heading'] ?? '';
$count   = absint( $attributes['count'] ?? 3 );

$posts = get_posts( array( 'numberposts' => $count, 'post_type' => 'myplugin_book' ) );
?>
<div <?php echo get_block_wrapper_attributes(); ?>>
    <?php if ( $heading ) : ?>
        <h3><?php echo esc_html( $heading ); ?></h3>
    <?php endif; ?>
    <ul>
        <?php foreach ( $posts as $post ) : ?>
            <li>
                <a href="<?php echo esc_url( get_permalink( $post ) ); ?>">
                    <?php echo esc_html( get_the_title( $post ) ); ?>
                </a>
            </li>
        <?php endforeach; ?>
    </ul>
</div>
```

`get_block_wrapper_attributes()` outputs the class and style attributes generated by the block supports (align, color, spacing) — omit it and those settings silently do nothing. It is already escaped.

Alternatively, `render_callback` in PHP:

```php
register_block_type( MYPLUGIN_DIR . 'build/feature-box', array(
    'render_callback' => 'myplugin_render_feature_box',
) );

function myplugin_render_feature_box( $attributes, $content, $block ) {
    return sprintf(
        '<div %s>%s</div>',
        get_block_wrapper_attributes(),
        esc_html( $attributes['heading'] ?? '' )
    );
}
```

**Escape in the render callback exactly as anywhere else.** Attributes are user input.

## Static blocks (markup saved to content)

The `save` function's output is stored in post content. Changing it later causes block validation errors on existing posts — which is why dynamic blocks are usually the safer choice for a plugin.

```js
import { useBlockProps, RichText } from '@wordpress/block-editor';

export default function save( { attributes } ) {
    const blockProps = useBlockProps.save();
    return (
        <div { ...blockProps }>
            <RichText.Content tagName="h3" value={ attributes.heading } />
        </div>
    );
}
```

If you must change saved markup, add a `deprecated` entry with the old `save` so existing content still validates.

## Edit component

```js
import { useBlockProps, RichText, InspectorControls } from '@wordpress/block-editor';
import { PanelBody, RangeControl, ToggleControl } from '@wordpress/components';
import { __ } from '@wordpress/i18n';

export default function Edit( { attributes, setAttributes } ) {
    const { heading, count, showIcon } = attributes;
    const blockProps = useBlockProps();

    return (
        <>
            <InspectorControls>
                <PanelBody title={ __( 'Settings', 'my-plugin' ) }>
                    <RangeControl
                        label={ __( 'Number of items', 'my-plugin' ) }
                        value={ count }
                        onChange={ ( v ) => setAttributes( { count: v } ) }
                        min={ 1 } max={ 10 }
                    />
                    <ToggleControl
                        label={ __( 'Show icon', 'my-plugin' ) }
                        checked={ showIcon }
                        onChange={ ( v ) => setAttributes( { showIcon: v } ) }
                    />
                </PanelBody>
            </InspectorControls>

            <div { ...blockProps }>
                <RichText
                    tagName="h3"
                    value={ heading }
                    onChange={ ( v ) => setAttributes( { heading: v } ) }
                    placeholder={ __( 'Heading…', 'my-plugin' ) }
                />
            </div>
        </>
    );
}
```

Use `useBlockProps()` in edit and `useBlockProps.save()` in save — without them the block ignores its supports and alignment.

## Fetching data in the editor

```js
import { useSelect } from '@wordpress/data';
import { store as coreStore } from '@wordpress/core-data';

const posts = useSelect(
    ( select ) => select( coreStore ).getEntityRecords( 'postType', 'myplugin_book', { per_page: 5 } ),
    []
);
```

For a custom endpoint, `apiFetch` — and remember the post type/meta must be exposed via `show_in_rest` for core-data to see it.

## Block categories

```php
add_filter( 'block_categories_all', function ( $categories ) {
    return array_merge( $categories, array( array(
        'slug'  => 'myplugin',
        'title' => __( 'My Plugin', 'my-plugin' ),
        'icon'  => null,
    ) ) );
} );
```

## Patterns and variations

A **pattern** is prebuilt content — often more useful than a new block:

```php
add_action( 'init', function () {
    register_block_pattern( 'myplugin/hero', array(
        'title'      => __( 'Hero Section', 'my-plugin' ),
        'categories' => array( 'featured' ),
        'content'    => '<!-- wp:heading --><h2>Hello</h2><!-- /wp:heading -->',
    ) );
} );
```

A **variation** is a preconfigured version of an existing block — cheaper than building one from scratch.

## Editor assets

`block.json`'s `editorScript`/`style` handle enqueueing. When you need extra editor-only assets:

```php
add_action( 'enqueue_block_editor_assets', function () {
    wp_enqueue_script( 'myplugin-editor', MYPLUGIN_URL . 'build/editor.js',
        array( 'wp-blocks', 'wp-element', 'wp-editor' ), MYPLUGIN_VERSION, true );
} );
```

Build with `@wordpress/scripts` (`wp-scripts build`), which generates an `.asset.php` file with the correct dependency array and version — use it:

```php
$asset = require MYPLUGIN_DIR . 'build/index.asset.php';
wp_enqueue_script( 'myplugin-block', MYPLUGIN_URL . 'build/index.js', $asset['dependencies'], $asset['version'], true );
```

## Block translations

```php
wp_set_script_translations( 'myplugin-feature-box-editor-script', 'my-plugin', MYPLUGIN_DIR . 'languages' );
```

JS strings use `__()` from `@wordpress/i18n` and need a JSON translation file — `.po` files alone do not reach JavaScript.

## Pitfalls

- **`apiVersion` below 3** — breaks in the iframed editor.
- **Not escaping in `render.php`** — block attributes are user input.
- **Omitting `get_block_wrapper_attributes()`** — supports silently stop working.
- **Changing a static block's `save` output** without a `deprecated` entry — validation errors on existing posts.
- **Registering blocks outside `init`.**
- **Hardcoding the script dependency array** instead of using the generated `.asset.php`.
- **Building a block when a pattern or variation would do.**
- **Meta not exposed with `show_in_rest`** — the editor cannot read or write it.
